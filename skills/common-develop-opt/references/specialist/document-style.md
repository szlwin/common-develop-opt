# 正式文档表达规范

## 快速规则

正式项目文档首先服务于人阅读，机器字段只用于稳定引用、校验和归档。正文直接说明业务事实、边界、原因和失败场景；不要写 Agent 的思考过程，也不要用空泛总结代替事实。

## 写作要求

- 使用项目已经确定的业务名称；同一概念不要为了“文采”反复换同义词。
- 一个段落回答一个问题。复杂规则先写结论，再写原因或例外。
- 表格只承载稳定结构化信息；解释性内容使用正常段落。
- 规则要写清 Owner、允许行为、禁止行为和失败后果，不写“保证稳定性”“提升可维护性”这类没有可验证含义的话。
- 示例只在帮助理解真实规则时使用，不为了凑完整度机械举例。
- Requirement、Design、Module Desc、Test Case 和页面设计中不得出现“本 Agent 认为”“综合以上分析”等工作过程措辞。
- revision、digest、schemaVersion、sourceRefs 等机器字段放在 front matter、表格或隐藏元数据中，不打断正文阅读。

## 推荐表达

不写：

> 通过上述设计，可以有效提升系统的可维护性、可扩展性和稳定性。

改为：

> 订单状态由 ORD 模块维护。履约模块只能通过已声明的业务接口推动订单状态变化，不能直接更新订单表。

## 校验

`python3 scripts/document_style.py --path <document-or-directory> --ready --json`

机器校验只检查可客观判断的问题：重复标题、未清理占位符、明确的套话黑名单、空章节和过长正文行。自然度、业务表达是否清楚仍由文档 Reviewer 判断，脚本不得用主观分数替代 Review。

`wk -d` preview 和 archive 会对即将生成的 requirement、module description 和 union language Markdown 执行同一套客观检查；发现重复标题或套话时在写入前失败。模板文件仍允许占位符，只有 `--ready` 检查才把占位符视为错误。
