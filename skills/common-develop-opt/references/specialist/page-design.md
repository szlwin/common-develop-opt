# 页面业务行为设计规范

## 快速规则

先确认当前任务的输入、revision、允许范围和停止条件。机器字段和参数边界统一见 [机器字段与状态边界](../core/machine-boundaries.md)。

## 详细规则

## 0. 页面设计快速规则 {#page-design-quick-rules}

页面设计记录业务可见状态、操作、校验、权限、导航、错误、后端交互和具体测试设计输入，但不演变为视觉设计规范。启用 `wk -v` 时将普通页面行为保留在 canonical design 的页面章节；只有稳定页面主题独立变更或需要独立 Review 时，才在所属模块的 `page-design/` 目录创建独立页面文档。

本文件只在版本工作模式启用 `wk -v` 时进入设计上下文。页面设计仅描述业务字段、操作、状态、权限、校验、反馈和交互路径，不包含配色、字体、图标、品牌、高保真原型、动效或像素级视觉设计。

## 1. 产出位置

```text
version/{VERSION}/module/{MODULE_CODE}/page-design/{PAGE_DOCUMENT_STEM}_design.md
```

这是新建和迁移页面文档的目标 canonical 布局。`{PAGE_DOCUMENT_STEM}` 使用稳定页面语义，可包含模块前缀和页面主题，但不得包含版本号、revision、Review 轮次、日期或临时任务编号。文件名不定义页面 Owner，也不要求把项目中的历史拼写推广为通用命名规则。

### 1.1 页面文档身份与 Owner

- 一个页面文档必须在“设计信息”中声明且只声明一个主 `PAGE-*`；同一文件可以包含该页面的子组件和多个 `PAGEACT-*`。
- Owner 模块由文档中的模块声明、目录 `{MODULE_CODE}` 和主页面编号共同确定，三者必须一致；主页面编号使用 `PAGE-{MODULE_CODE}-*`。
- 由 Owner 模块定义的操作使用 `PAGEACT-{MODULE_CODE}-*`。页面复用其他模块已定义的操作时，必须链接原操作及原页面文档，不得复制后改名。
- 总览、Workbench 或跨模块设计可以引用其他模块页面，但不得因引用关系改变页面 Owner，也不得复制一份正文形成第二事实源。
- 移动页面文档时，除非同时存在经确认的 Owner 修正，否则保持原 `PAGE-*`、`PAGEACT-*` 稳定 ID；目录、文件名和 Markdown 链接可以变化，稳定 ID 不随路径变化。

### 1.2 旧布局兼容与冲突

旧布局仅作为迁移期只读输入兼容：

```text
version/{VERSION}/module/{MODULE_CODE}/{MODULE_CODE}_page_design.md
```

- 不再按旧布局创建新页面文档。
- 迁移使用“移动并更新全部入链/出链”，不得保留内容副本或用两个文件共同维护同一页面事实。
- 新旧布局声明同一主 `PAGE-*`，或多个新文件声明同一主 `PAGE-*` 时，必须 fail-closed；不得按文件时间、路径优先级或内容猜测自动选取。
- 旧文件被迁移后，其旧路径不得继续作为 canonical 链接；调用方必须更新为从声明文档出发可解析的新相对路径。

### 1.3 运行时支持与迁移边界

页面模板、上下文路由、模块逐页索引、版本门户、归档器和 Markdown 路径/fragment 校验均按新布局工作。旧 `{MODULE_CODE}_page_design.md` 仍是只读兼容输入；历史页面只有在显式迁移并更新全部入链/出链后才进入新布局。自动发现支持新格式 `*_design.md` 与旧聚合文件，不会把其他历史命名的页面文件自动解释为主页面；迁移前必须先形成清单，不得用新生成结果覆盖未识别的历史事实。

未启用 `wk -v` 时：

- `work.md#页面设计` 必须为“无”；
- 不创建新的页面设计文档；
- 后续开发只能复用已有页面行为事实和现有代码，不得临时扩展页面交互需求。

## 2. 责任 Agent

- `DesignAgent`：在 design revision 中创建或更新页面业务行为设计。
- `RequirementReviewAgent`：核对页面行为是否覆盖已确认需求。
- `DesignReviewAgent`：核对页面状态、权限、错误和接口交互是否完整。
- `DevelopAgent`：只按已通过的页面行为设计实现，不补做产品或视觉决策。

## 3. 最小结构

1. 唯一主页面标识、页面中文名称、稳定页面主题和可选子组件；
2. 关联需求、功能、规则和验收 ID；
3. 角色与数据权限；
4. 展示字段及来源；
5. 查询、筛选、排序和分页；
6. 操作入口、前置条件和可见/可用状态；
7. 表单字段、默认值、校验和提交；
8. 加载、空数据、成功、失败、部分成功和重试状态；
9. 接口交互与错误语义；
10. 禁止副作用和可观察验收；
11. 追踪关系；
12. 提供给测试设计的具体输入示例、可观察输出、验证方式和 Case 引用。

### 3.1 链接与追踪表约束

- 页面文档中的 Markdown 链接必须从当前页面文件所在目录计算相对路径；不得写个人目录、仓库绝对路径或依赖旧 canonical 路径。
- “设计信息”必须给出主 `PAGE-*`、页面中文名称和原型图入口。存在原型时链接到真实原型文件；不存在时写“不适用”及原因，不得制造占位目标。
- 接口表必须同时提供接口中文名称、可点击的接口契约引用和详细业务语义；中文名称必须与目标 API 文档一致，链接必须定位到具体接口而不是只打开 API 文件。
- “禁止副作用与验收”中的追踪编号保持纯文本；验收编号链接到 Requirement 文档中同名的显式 `AC-*` anchor，不依赖渲染器自动生成的中文标题 fragment。
- “追踪关系”每行只表达一个 `功能编号 → 流程编号 → 步骤编号 → 验收编号` 映射。功能编号旁必须提供功能中文名称；功能、流程、步骤和验收引用分别链接到其 canonical 定义，不得把多个编号堆在同一单元格。
- 模块说明的页面设计入口必须逐页链接到 Owner 文档；不得只链接旧 `{MODULE_CODE}_page_design.md` 或复制页面正文。

## 4. 门禁

- 启用 `wk -v` 的功能，其 `work.md#页面设计` 不得为空或为“无”；
- 页面行为必须引用稳定需求/功能/验收 ID；
- 每个适用 `PAGEACT-*` 必须映射需求目录下 `test_case.md` 的 `CASE-*`；Case 必须反向引用 `PAGE-*`、`PAGEACT-*` 和页面设计相对链接；
- 页面设计必须为关键操作给出具体输入示例、可观察输出和推荐验证方式，但不得代替测试设计的数据准备、清理和自动化映射；
- 不得锁定视觉风格；
- 页面行为变化必须使相关设计、测试、实现和验证追踪项重新评估。

## 5. 关联页面查询与选择返回

适用于“选择员工 → 打开员工查询 → 筛选 → 选中 → 确认 → 原页面回填”，也适用于抽屉、路由跳转和内嵌选择器。展示方式不决定 Owner：专用于当前页面的子组件可保留当前主 `PAGE-*`；有独立业务职责、可复用或需要独立 Review 的选择页由其所属模块定义独立主 `PAGE-*`，即使以弹窗展示也不复制到调用方。独立权限本身不强制拆文档。

调用方维护唯一的调用与返回约定；目标页面维护查询、权限、选择行为和反向入口。目标可以有多个调用方，每个调用方使用不同关联编号；反向入口只保存编号和链接，不复制回填约定。当前页面子组件用指向自身文档的链接，同样区分打开操作和确认操作。

### 5.1 结构化关联表

模板的 `PAGE-RELATIONS` 表用于调用方，`PAGE-CALLERS` 表用于目标方。关联编号为 `PAGEREL-{来源模块}-{稳定主题}`；它是页面交互引用，不创建另一套业务 FLOW。表头和标记按模板保留；无关联时保留空表或省略此节，不能填占位行。旧文档缺少表时不推断“已覆盖关联”，新增或修改选择返回行为时必须补表。

- 来源操作、目标操作分别在两份文档的“操作与状态”表第一列定义，不能用正文提及的 ID 代替定义。目标操作通常为确认选择；查询、取消等其他操作也必须在目标页面描述。
- 目标页面与反向来源页面使用一个 `[PAGE-*](相对路径)` 链接，标签必须等于目标文档的主页面编号。链接按当前文件计算，可指向显式锚点；关联表单元格使用行内链接，不使用引用式缩写。
- 展示方式：`MODAL`、`DRAWER`、`ROUTE`、`INLINE`；选择方式：`SINGLE`、`MULTIPLE`、`NONE`。
- 输入上下文写清组织/权限范围、默认筛选、已选值和重新打开时的状态。调用参数不能扩大服务端权限。
- 返回与回填写清稳定标识、展示字段、字段映射、替换/追加与去重，以及是否只更新草稿或立即持久化。无返回行为时写明原因。
- 取消行为写清关闭、取消、返回导航时原字段与未保存输入如何处理。另在操作表覆盖无数据、未选择、失效员工、无权限、失败重试；多选时说明跨页选择和数量限制。

### 5.2 检查与阶段边界

版本门户和归档预览使用同一关联校验：目标文件、主页面身份、操作定义、关联编号唯一性、枚举和反向入口必须有效；已有页面的重复主 ID 门禁仍然适用。支持同一次写入的 pending 文档，不为检查关系自动修改被引用页面。

设计阶段不要求提前创建测试 Case。测试设计阶段在 `test_case.md` 的关联事实中记录 `PAGEREL-*`，并填写 `TEST-CASE-PAGE-RELATIONS` 表；`case_doc.py validate --stage ready` 核对来源关联、两侧页面与操作的追踪、验证场景和返回断言。每组关联按适用性覆盖确认回填、取消不改值、查询失败、权限、空结果和重复打开；一个 Case 可以只覆盖一个分支，完整分支覆盖由 TestDesign/Review 核对。

机器检查证明结构和引用一致，不能证明字段映射、业务语义或测试执行正确。流程、页面、Case 的现有 revision/STALE 规则继续生效。例子见 [页面示例](page-design-example.md#关联页面选择返回示例)。


## 流程追踪

页面入口、操作和状态变化必须引用适用 `FLOW-*` 与 `STEP-*`。页面只描述用户可观察行为，不复制完整流程；同一操作的成功、失败和重试状态必须与业务流程和验收标准一致。流程变更后页面设计 revision 需要按影响标记 STALE。
