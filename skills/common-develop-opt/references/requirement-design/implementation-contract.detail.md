# 前后端实现契约规范

## 0. 实现契约快速规则 {#implementation-contract-quick-rules}

实现契约将需求、当前实现证据、`IMPL-DEC-*`、设计、API/数据行为、表/字段读写和持久化时机、原函数兼容性、代码变更位置、失败处理、副作用和验证绑定到同一个 revision。每个对象遵循 `REUSE → COMPATIBLE_EXTEND → MODIFY → CREATE`；`CREATE` 必须记录排除前序方案的证据、共享逻辑处置方式和 Owner。canonical `*_design.md` 必须通过 `design_doc.py validate --stage ready`。

本文件定义设计完成后、编码前的实现契约。`*_design.md` 无论是否启用 `wk -mc` 都必须达到可直接实施的低歧义程度；`wk -mc` 只控制是否额外生成前后端伪代码文档，未启用时 `work.md` 的前端伪代码、后端伪代码填写“无”。实现契约只描述业务行为、数据、接口、权限、状态和错误，不描述颜色、排版、动效或其它视觉设计。

## 1. 目标

实现契约用于：

- 把设计转成开发可执行的模块、方法和组件边界；
- 明确输入、输出、前置/后置条件、失败语义和副作用；
- 建立测试 Case 与实现 seam 的映射；
- 控制 Agent 允许修改的文件和复用边界；
- 避免直接从模糊自然语言生成代码。

## 2. 进入条件

第一条件是当前版本 `work.md` 已声明 `model_code=true`，即使用了 `wk -mc`。未启用时不得为了模板完整生成 `{MODULE_CODE}_web_code.md` 或 `{MODULE_CODE}_back_code.md` 伪代码文档。

上述条件仅适用于额外伪代码产物。主设计文档始终使用 `assets/documents/structured-docs/design.template.md` 的实现就绪矩阵，并通过：

```bash
python3 scripts/design_doc.py validate -g DesignReviewAgent --file {DESIGN_FILE} --stage ready --json
```

主设计不能把关键实现语义推迟到可选伪代码阶段。

启用后，只有在以下条件满足后才生成实现契约：

1. 需求分析、业务模型和设计使用当前有效 revision；
2. 设计阶段的 ArchitectureReview 与可测性 Review 已通过；
3. 标准模式下适用测试 Case 已明确；`wk -min` 时改为需求验收条件和设计分支已明确；
4. 关键业务决策无未决 P0/P1；
5. 目标代码和可复用实现已调查。

## 3. 输入

- 需求、验收标准和追踪 ID；
- 业务模型、不变量、状态机和业务错误；
- API、DB、事务、幂等、并发和异常设计；
- 标准模式下的测试用例与测试数据；`wk -min` 时不要求该输入；
- 现有模块、相似实现和项目规则；
- 适用的需求/功能关系、影响策略与跨模块实现映射 revision；
- 代码注释规范和现有项目注释风格；
- `backend-code-reference.md`、`web-code-reference.md`、`tdd-core` 与 `test-matrix-design`；需要具体测试边界时按需读取 `test-seam`。

## 4. 输出

以下输出只在 `wk -mc` 启用时适用：

```text
DOC_ROOT/version/{VERSION}/module/{MODULE_CODE}/
├── {MODULE_CODE}_web_code.md
└── {MODULE_CODE}_back_code.md
```

项目已有其它事实路径时沿用现状。输出必须有 revision，并在 `traceability.json` 中被引用。

### 4.1 实现策略决策

每个接口、方法、组件、数据访问逻辑和业务规则先形成 `IMPL-DEC-*`，并按 `REUSE → COMPATIBLE_EXTEND → MODIFY → CREATE` 决策。后一策略必须有前序策略不适用的当前代码证据；`CREATE` 还要记录公共逻辑处置、唯一 Owner、跨模块依赖和验证范围。枚举、抽取判断、自动返修与停止边界只读取 `implementation-strategy.md`。

代码蓝图、`development_task_plan.json`、必要代码注释、兼容验证和 Review Evidence 必须引用同一个 `IMPL-DEC-*`。开发时发现现有代码证据失效，返回 Design 更新 revision，不在实现阶段自行改为平行新建。

## 5. 前端实现契约

前端契约只覆盖业务交互和代码实现。按信息充分程度选择：

| 等级 | 适用条件 | 输出 |
|---|---|---|
| `NONE` | 需求、界面行为、API、目标文件和测试路径已足够直接实施 | 最小引用记录 |
| `LITE` | 已有页面/组件的局部业务差异 | 只写变化和影响 |
| `FULL` | 新组件、复杂状态、多接口、复杂权限、批量或步骤流程 | 完整 Frontend Code Spec |

等级不足时必须升级，不能为减少文档而隐藏实现缺口。

### 5.1 最小记录

```md
## {FEATURE_CODE}

- 等级：NONE
- 需求/界面行为：`{REQUIREMENT_OR_DESIGN_REF}`
- API：`{API_REF}`
- 目标文件：`{REAL_PATH}`
- 复用参考：`{EXISTING_CODE_REF}`
- 验收追踪：`{TR_IDS}`
- 测试入口：`{TEST_PATH_OR_COMMAND}`
- 判定证据：...
```

### 5.2 LITE/FULL 必须覆盖

- 目标文件和开发模式：create / update / patch；
- 查询、列表、表单、弹窗和操作的业务字段；
- 显示、禁用、权限和业务前置条件；
- 加载、空数据、成功、失败、无权限和并发冲突状态；
- API 请求、响应、分页、错误和重试语义；
- 枚举、脱敏、数据范围和字段转换；
- 标准模式下的组件、接口、单元或 E2E 测试 seam；`wk -min` 时省略测试实现内容；
- 需要后端新增或修改的契约；
- 明确的用户确认项。

前端契约不得指定视觉风格。现有代码参考只用于复用组件、目录、状态管理和编码模式。

## 6. 后端实现契约

每个业务入口至少说明：

- 功能与方法 ID；
- 输入 DTO、输出 VO；
- 前置条件和后置条件；
- 参数、权限和数据范围校验；
- 业务不变量与状态转换；
- 读取和写入的数据；
- 事务、幂等、锁和并发处理；
- 外部依赖、超时和失败策略；
- 业务错误码与异常类型；
- 副作用、事件和审计；
- 调用关系；
- 标准模式下的 Case ID 与测试 seam；`wk -min` 时不编写；
- 复杂度和拆分边界；
- 公共契约注释要求和必须解释的关键分支；
- 关联影响策略与跨模块实现映射步骤引用。

可使用 `backend-code-reference.md` 的轻量 DSL，但 DSL 只表达契约，不要求生成大量代码。

### 6.1 数据读写与保存契约

每个重要业务动作必须在主设计的数据访问矩阵中逐行说明：触发入口、表/聚合、SELECT/INSERT/UPDATE/DELETE、字段、查询或更新条件、锁与读取一致性、首次写入与后续更新时机、Repository/Mapper 保存和 flush 时机、事务边界、失败后保留的事实及追踪 ID。只列字段定义而不说明谁在何时读写，不能进入开发。

新增或修改字段还必须说明业务作用、值来源、空值/默认值、是否可变、唯一性/索引/外键、历史数据回填、兼容读写窗口和回滚。API 字段必须映射到校验、命令/领域字段、表字段或下游契约，以及响应/事件字段，禁止留下 DTO 到持久化之间的隐含转换。

### 6.2 原有功能与代码改动契约

对已有功能必须同时记录当前代码/配置/接口证据、调整前后行为、受影响调用方、数据与 API/UI 兼容、回归范围及发布回滚注意事项。代码蓝图至少定位到仓库/模块、现有或建议新增的文件/类/配置、方法/符号、具体改动、职责、依赖、实施顺序和对应测试；不存在的路径必须标为“建议新增”，不能伪造成当前事实。


## 7. 跨模块实现契约

跨两个及以上模块时，实现契约引用 `dependency_impact.yaml#CMI-*` 及其 `CMSTEP-*`，并同时标明对应业务 `FLOW/STEP`，逐步写明：

- owner 模块和调用方向；
- API、事件、回调或定时契约；
- 本地事务和不可跨越的事务边界；
- 幂等键、超时、重试、乱序和重复消息；
- 每个失败点的最终状态、补偿和人工恢复；
- 端到端 trace/correlation ID；
- Case 与测试 seam。

不得使用“调用其它模块处理”“失败后回滚”等不可执行描述。

## 8. 代码注释契约

实现契约应列出需要稳定注释的公共入口和关键分支，但不预写逐行注释。至少标注：

- 需要说明的业务不变量或决策 ID；
- 事务、幂等、补偿、兼容或安全原因；
- 错误修改可能产生的业务后果；
- 注释应位于接口、方法还是具体分支附近。

详细格式见 `code-comments.md`。

## 9. 复杂计算与条件分支

涉及多表读写、map/filter/reduce、求和、生成新数据或复杂 `if/else` 时，不把全部逻辑压缩成单条规则。按以下层次表达：

```text
use case
  → decision table / state rule
  → named calculation step
  → data read/write step
  → side-effect boundary
```

每个步骤写明：

- 输入数据和来源；
- 分支条件；
- 算法或业务公式；
- 输出；
- 失败语义；
- 是否纯函数；
- 是否在事务内；
- 对应测试。

复杂分支优先使用决策表或显式规则函数，不生成难以 Review 的嵌套配置。

## 10. TDD 映射

标准模式下实现契约必须包含测试矩阵：

| Case ID | 目标方法/组件 | 场景 | 初始状态 | 输入 | 预期输出/错误 | 预期状态/副作用 |
|---|---|---|---|---|---|---|

新行为和 BUG 修复先运行目标测试取得有效 RED，再最小实现 GREEN，重构后重跑。纯重构必须先取得当前 GREEN 表征基线。

使用 `wk -min` 时本节整体不适用：不创建测试矩阵、不编写测试代码，也不产生 RED/GREEN/REFACTOR 测试证据。伪代码仍必须完整表达需求分支、错误和副作用，不能用“后续测试确认”作占位。

## 11. Review 门禁

进入开发前，标准模式由 PlanReviewAgent、TDDReviewAgent 和 DevelopAgent 分别检查；`wk -min` 时不分派 TDDReviewAgent，由 PlanReviewAgent、DevelopAgent 检查非测试项：

- 契约是否覆盖适用追踪项；
- 是否复用现有能力而不是平行重写；
- 是否遵循当前 `IMPL-DEC-*` 与四级顺序，`CREATE` 的排除理由、职责和公共逻辑 Owner 是否成立；
- 是否同时避免同一业务规则多事实源，以及布尔/模式参数、跨域 switch、万能工具类造成的伪复用；
- 文件、模块和调用边界是否明确；
- 分支、错误、事务和并发语义是否可测试；
- 关系影响、跨模块失败/补偿和注释契约是否完整；
- 是否存在占位符、伪造路径或未确认假设；
- 是否混入视觉设计或其它越界内容。

## 12. 代码反向同步

实际代码先于文档变化时：

1. 读取真实 diff 和验证结果；
2. 更新对应契约，标记“根据实际代码反向同步”；
3. 重新评估需求、设计和测试追踪；
4. 触发独立 Review；
5. 旧 revision 和旧证据不得继续作为当前完成依据。


## 业务流程实现映射

涉及结构化业务流程时，前后端实现契约必须记录 `flow_refs` 和 `flow_step_refs`，将用户操作、服务方法、API/事件、事务、错误与补偿映射到稳定 FLOW/STEP。实现契约不得改变流程目标、顺序或失败语义；如需改变，先重开 requirement_analysis。
