# common-develop 范围边界

本文件是判断任务是否应进入 `common-develop` 的唯一范围事实。范围判断先于任何需求、设计、编码或测试动作。

## 1. 范围内能力

### 1.1 需求与业务

- 需求确认、澄清、范围锁定和用户决策记录；
- 需求分析、业务规则、验收标准、影响范围和优先级依赖；
- 需求—需求、需求—功能、功能—功能的机器可读关系，以及由同一事实生成的关联图；
- 删除、取消、失效、迁移、替代、退款、库存释放等关联对象处置策略；
- 商品、订单、库存、支付、物料等跨模块业务流程、失败路径和补偿；
- 业务建模、统一语言、实体、值对象、聚合、不变量、状态机、命令、事件与业务错误；
- 需求、业务模型和设计之间的追踪与一致性验证。

### 1.2 设计与计划

- 模块边界、接口、数据、持久化、事务、幂等、并发、异常和日志设计；
- 可测性、测试 seam、测试数据和回滚/补偿设计；
- 实施任务拆分、依赖图、允许修改范围、输入输出和验证命令；
- 接口、公共方法和关键业务分支的代码注释契约、实现规范及 Review；
- 需求、业务模型、设计、计划等产物的独立 Review 和交叉质询。

### 1.3 实现与验证

- TDD、编码、重构、静态检查、构建和自动化测试；
- BUG 复现、根因定位、最小修复、回归测试和复盘；
- Code Review、Spec 符合性 Review、工程规范 Review，以及按代码范围触发的安全、性能、数据迁移、API 契约、并发、可维护性和测试专项 Review；
- 长任务、多 Agent 调度、checkpoint、handoff、恢复和完成证据核验。

## 2. 明确排除

### 2.1 视觉设计

不处理：

- 视觉风格、配色、字体、图标、品牌和审美判断；
- 高保真原型、视觉稿、动效和设计系统；
- 视觉一致性 Review、截图审美比较或像素级验收。

允许处理：

- 页面承载的业务字段和操作；
- 权限、状态、出现/可点/禁用条件；
- 交互步骤、业务反馈、错误提示语义；
- 可自动化测试的元素标识与行为。

页面相关产物应称为“界面行为规格”或“交互业务规格”，不得称为视觉设计稿。页面业务行为设计只有在版本使用 `wk -v` 时进入当前工作范围；未启用时 `work.md#页面设计` 必须为“无”。`wk -min` 只控制测试阶段，不改变页面设计开关；视觉设计始终排除。

### 2.2 商业与产品经营

不处理商业计划、市场规模、竞品营销、定价、增长、销售、融资、品牌传播和经营预测。业务需求中的成本、合规或业务价值可作为约束，但不扩展为商业计划 Agent。

### 2.3 发布与运营

不处理发布部署、CI/CD 上线、灰度、商店上架、发布说明、上线传播、运营值守或生产发布审批。`wk -gc` 默认仅在任务分支创建顺序本地阶段 Commit；只有显式 `wk -gp` 且 `wk -gc` 同时启用时，才允许把当前 checkpoint 同步到当前分支配置 remote。native Git transport 不可用时可对 github.com 使用严格 GitHub Connector fallback，但只允许当前 checkpoint 的 exact Git Data publish/verify；仍不执行 Git merge、PR 创建、临时 branch/workflow、tag push、Release 或部署。若设计需要说明兼容性、迁移顺序或回滚能力，可以记录为技术约束，但不执行发布流程。`wk -d` 的版本增量归档只更新研发全量事实文档，不属于发布审批。

### 2.4 泛 QA

不处理没有明确需求/设计基线的泛探索式 QA、视觉 QA、设备矩阵、发布就绪检查、运营验收或“整体体验打磨”。TestAgent 仅对已确认追踪项和风险执行测试。

## 3. 边界场景

| 用户请求 | 是否进入 | 处理方式 |
|---|---|---|
| “设计登录页面的字段、权限和错误提示” | 有条件 | 仅在 `wk -v` 启用时作为界面业务行为设计；`wk -min` 只影响测试阶段，不关闭页面设计。 |
| “把登录页做得更高级、更漂亮” | 否 | 视觉设计，停止并说明越界。 |
| “设计订单状态机、API 和表结构” | 是 | 业务建模与技术设计。 |
| “制定产品商业化路线和定价” | 否 | 商业计划。 |
| “编写并执行自动化回归测试” | 是 | 有需求/设计基线时进入测试。 |
| “上线前全面 QA 一遍” | 否或需重述 | 需转成明确追踪项和测试范围，否则属于泛 QA。 |
| “设计数据库迁移及回滚方案” | 是 | 技术设计与 Review；不执行生产发布。 |
| “把版本部署到生产” | 否 | 发布部署。 |

## 4. 混合任务拆分

一个请求同时包含范围内和范围外内容时：

1. ProjectManagerAgent 将请求拆分成独立目标；
2. 只把范围内目标进入 `common-develop`；
3. 范围外目标记录为 `OUT_OF_SCOPE`，说明原因和依赖；
4. 范围外目标不得偷偷嵌入需求、设计、测试或 Review 的完成标准；
5. 若范围内目标依赖范围外决策，任务设为 `WAITING_USER` 或 `BLOCKED`，不得自行补齐。

## 5. 范围门禁输出

范围判断至少输出：

```yaml
scope_result:
  in_scope: true
  included:
    - requirement_analysis
    - business_model
  excluded:
    - visual_design
  assumptions: []
  blocking_dependencies: []
  decision: PROCEED
```

`decision` 只使用：

- `PROCEED`：全部必要工作在范围内；
- `PROCEED_WITH_SPLIT`：已剥离范围外目标；
- `WAITING_USER`：边界或依赖需用户决策；
- `OUT_OF_SCOPE`：请求不属于本 Skill。
