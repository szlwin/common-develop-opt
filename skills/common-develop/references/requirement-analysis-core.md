# 需求分析执行核心

## 1. 分析对象
RequirementAnalysisAgent 在已确认的同一份 `requirement.md` 中补全功能、业务规则、异常、约束和影响，不创建平行分析文档。一个需求可以包含多个功能；只有能独立确认、延期、回退或拥有独立业务目标的内容才拆成新需求。

## 2. 必查维度
逐功能分析角色与权限、输入输出、默认值、状态变化、幂等、并发、事务、错误、超时、部分成功、补偿、历史数据和非功能约束。主动质询空值、极值、重复、乱序、非法状态、越权、并发竞争、重试和旧客户端。

需求分析阶段只定义可验证的业务边界、正常/边界/失败语义及其追踪输入，不要求已经存在测试文件或测试 Case。Case 覆盖矩阵由后续 `test_design` 阶段建立，真实命令和执行 Evidence 由 `testing` 阶段提供。

## 3. 稳定标识
需求、功能、规则、异常、验收和追踪使用语义契约中的稳定命名空间。重要规则无法得到唯一预期时登记 `AMBIGUITY` 或 `CONFLICT`，退回需求确认，不用实现默认值掩盖决策缺口。

## 4. 影响边界
先检索相同业务概念的既有能力，再决定复用、扩展或替换。发现端到端流程、对象关系、跨模块协作或历史数据影响时，加载对应细分 Reference，不在基础分析中默认展开整个依赖图规范。

## 5. 人类可读性
先更新 `1.1 阅读摘要`，再补充规则、异常、AC 和追踪表。正文先解释业务行为和示例，再给稳定 ID；不要让读者通过几十个 `BR/AC/TR` 反向猜目标。追踪、Evidence、Reviewer 和历史 revision 只引用，不复制到需求正文。需求分析继续维护唯一 `requirement.md`，不得按轮次创建平行文件。
